# 앱 내 웹 번들 업데이트 구현 계획

**목표:** 설정 버튼으로 서명된 웹 번들을 확인·적용하고 부팅 실패 시 복구한다.

**설계:** [설계 문서](../specs/2026-10-18-in-app-ota-design.md). 사용자 지침에 따라 별도 워크트리에서 자율 실행하며 네이티브와 산출 도구는 독립 작업으로 나눈다. 배포는 이 작업에 포함하지 않는다.

## 1. Android 업데이트 경계

- `AppUpdatesPlugin`, 순수 Java 검증·복구 코드, `MainActivity`, Gradle 설정을 담당한다.
- getStatus/check/apply/ready 인터페이스와 서명 envelope는 설계 문서를 따른다.
- 서명 변조, ZIP 경로 탈출·중복·크기, sequence 재생, APK 불일치, pending 복구 테스트를 먼저 실패시킨 뒤 구현한다.
- 기존 Gradle JUnit과 assembleDebug로 검증한다. 의존성을 추가하지 않는다.

## 2. 웹 UI와 부팅

- `src/updates.ts`는 네이티브 경계와 웹 미지원 상태, `src/app.ts`는 확인·적용 상태 및 시트, `src/main.ts`는 첫 렌더 후 ready를 담당한다.
- 확인 실패를 최신으로 오인하지 않는지, 취소하면 적용되지 않는지, 연속 클릭이 중복 적용되지 않는지 먼저 테스트한다.
- `e2e/updates.spec.ts`에 업데이트 화면과 상태를 추가하고 `expectCleanLayout`을 실행한다.

## 3. 로컬 업데이트 산출 도구

- `scripts/build-ota.mjs`는 전용 빌드 provenance와 CLI 입력을 검증한 뒤 bundle.zip과 서명된 manifest.json을 만든다.
- 테스트는 도구를 직접 실행하고 생성 ZIP·서명을 독립적으로 읽어 검사한다. 데모·HTTP·symlink·잘못된 키를 거절하는지 확인한다.
- `vite.config.ts`, npm 스크립트, 검증 스크립트와 운영 문서에 사용법을 연결한다.

## 4. 통합 검증

- 전체 Vitest, 앱·e2e·monitor 타입 검사, production 빌드, Node 산출 도구 테스트, Java 유닛·APK 빌드를 실행한다.
- 새 Playwright 흐름을 밝은·어두운·좁은 화면에서 검사한다. 가능한 경우 로컬 에뮬레이터의 네이티브 경계도 확인한다.
- 검증에서 드러난 문제를 수정하고 코드 리뷰를 수행한다. 결과 보고는 로컬 검증과 실서비스 배포를 구분한다.

## 완료 증거

- `npm test`: 19파일, 367개 통과. 앱·e2e·monitor 타입 검사 및 Node 구문 검사 통과.
- `npm run build`, 운영 HTTPS 설정의 `npm run build:ota`: 통과.
- Android `:app:testDebugUnitTest :app:assembleDebug`: 26개 테스트와 APK 빌드 통과.
- Playwright 설정·즐겨찾기·업데이트 19개 검사 통과. 최종 업데이트 전용 9개 검사도 밝은·어두운·좁은 화면에서 통과.
- `test:ota:device`(emulator-5554): 실제 서명 HTTPS 다운로드, 변조 거절, 새 문서 적용, 이전 화면 ready 거절, 재실행·세션 유지, 30초 복구, 실패 sequence 거절, 미확정 상태 종료 후 복구와 정리까지 exit 0.
- 독립 소스 리뷰의 개인키 혼입·비동기 응답·ready 세대·Activity 수명 경계 지적을 회귀 검사와 함께 보완했고 최종 중요 결함 없음 판정을 받았다.
- 운영 배포·실제 예약·계정 등록은 하지 않았다. OTA 주소와 공개키를 설정한 지원 APK/AAB를 배포해야 기존 사용자에게 활성화된다. 작업은 `feat/in-app-ota` 워크트리에 보관한다.

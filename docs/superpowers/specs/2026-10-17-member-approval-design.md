# 회원 승인 설계

사용자가 동의한 방향: 초대 코드 없이 가입하고 로그인하지만, 관리자가 승인하기 전에는 철도 기능을 이용하지 못한다. 기존 회원은 이용 권한을 유지한다. 별도 워크트리에서 구현하고 로컬 검증까지 완료한다. 운영 데이터 변경·서버 재시작·배포는 범위 밖이다.

## 계약

- 사용자 `status`: `pending`, `approved`, `rejected`. 기존 SQLite 사용자에는 `approved`를 채우고 새 가입에는 명시적으로 `pending`을 쓴다. 관리자는 항상 승인 상태다.
- 회원 가입은 아이디·비밀번호와 선택적 `applicationNote`(최대 200자)를 받는다. 메모로 관리자가 신청자를 구별한다. 초대 코드 입력·발급 UI/API/CLI를 제거한다. Google 신규 가입은 추가하지 않으며 기존 Google 연결 로그인은 유지한다.
- 공개 사용자에는 `status`, `applicationNote`, `createdAt`을 추가한다. 기존 생성 시각을 추측하지 않고 `null`로 둔다.
- 대기·거절 회원의 세션은 유효하다. `POST /bootstrap`은 철도 저장소에 접근하지 않고 비어 있는 안전한 BootstrapState와 사용자 상태를 반환한다. 이 상태에서는 로그아웃·비밀번호 확인 후 탈퇴만 추가로 허용한다. 그 밖의 앱 API와 OAuth/MCP는 서버에서 승인 여부를 검사한다.
- 관리자 `GET /admin/users` → `{users: AppUser[]}`; `POST /admin/users/<id>/approval` 본문 `{status: 'approved' | 'rejected'}` → `{user: AppUser}`. 서버에서 관리자 역할을 확인한다. 대기·거절 사용자는 승인할 수 있다. 승인된 계정은 이 API로 거절할 수 없다(409): 실행 중 검색을 중단시키는 별도 정지 기능은 만들지 않는다. 동일 결정은 재시도 가능하다. 관리자 자신·다른 관리자 상태 변경은 금지한다.
- 대기 화면은 승인 대기 안내·신청자·상태 새로고침·로그아웃·탈퇴를 제공한다. 거절은 별도 안내다. 승인 후 같은 세션으로 홈에 진입한다. 대기 상태에서는 철도 상태·알림 폴링을 하지 않고 승인 상태만 안전한 bootstrap으로 확인한다.
- bootstrap 읽기는 20초 제한을 두어 응답이 멈춰도 다시 시도하거나 로그아웃할 수 있게 한다. 예약 등 변경 요청에는 이 제한을 적용하지 않는다. 관리자 목록 응답은 처리 중인 승인 결정과 최신 조회 결과를 오래된 상태로 덮어쓰지 못한다.
- 관리자 설정의 회원 관리는 대기자 목록(아이디·메모·신청 시각), 승인·거절, 승인/거절 상태를 제공한다. 메모·아이디는 HTML escape한다. 실패는 빈 목록/미승인을 뜻하지 않고 명확한 오류와 재시도를 제공한다.

## 검증

이전 DB 마이그레이션과 세션 유지, 무초대 가입, 관리자/회원 분리, 대기·거절 API 및 OAuth/MCP 차단, 승인 즉시 사용, 탈퇴, 결정 재시도·경쟁을 서버 테스트로 확인한다. UI 테스트와 Playwright 실서버 흐름에서 가입→대기→관리자 승인→동일 로그인으로 이용, 거절, 관리자 목록 실패를 확인하고 새 상태를 `expectCleanLayout`으로 측정한다. 기존 앱·서버 검사와 통합·헤드리스 E2E를 실행한다.
